# Independent oracles

`brute.py` answers Problems 1–4 by brute force on the region model of
[`docs/DESIGN.md`](../../docs/DESIGN.md) ("Semantics (default mode)"), and checks witness
paths. It is test code only. It imports nothing from `cyber_detectives`: it reads maps,
stories and histories in the fixture JSON form itself. It was written from DESIGN.md and
the paper notes, without reading `engine.py` or `problems.py`.

The tests that use it:

- `tests/test_oracle_self.py` checks the oracles without the engine. They must reproduce
  every Problem 1–4 expectation in `tests/fixtures/paper/*.json` and replay every fixture
  witness walk. The path checker must accept the original's valid paths and reject its
  known-bad ones (bugs B3, B5, B8). Random simulated walks must come out consistent, and
  the verdicts must satisfy a few implications (listed below).
- `tests/test_oracle_random.py` runs seeded random differential tests of the engine against
  the oracles (details below).

## The model

A *place* is a room, a free region (the papers' `R_k`), or the inside of an occupancy
region. The *window* `j` is the gap between recordings `j` and `j+1`. The agent starts
inside `p_1` and must end inside `p_n` after the last recording, with the whole story
reported.

Some moves need no recording and no story element. They depend on the window:

- Leaving a room is always silent.
- Entering a room is silent only with `unreported_visits=True` (or outside the story's
  interval, Problem 2). Otherwise it consumes the next story element.
- An occupancy region can be entered or left silently only in multi-agent mode, while the
  sensor is active.
- A single agent may leave an occupancy region after its deactivation.
- A beam can be crossed silently only while the sensors are off (Problem 2).

Each recording then acts on the agent:

- Single agent: a beam recording is a crossing, an activation is an entry, and a
  deactivation finds the agent inside.
- Multi-agent: x crosses at a beam recording or someone else did. Occupancy recordings only
  toggle whether the region is open, and x must not be inside at a deactivation.
- In both modes, histories that do not alternate A/D per occupancy sensor, and beam "D"
  events, are malformed, which means inconsistent.

## Methods, and why they are independent

The engine uses a dynamic program over `(position, story index)` states, one layer per
recording (DESIGN.md "Algorithm"). It shares states across all ways of reaching them, and
it computes Problems 3 and 4 by 0–1 BFS over the same product. The oracles avoid all of
that.

| Oracle | Method |
|---|---|
| `consistent` (Problem 1) | **Enumerate interleavings.** A candidate explanation fixes the window in which each story element `p_2..p_n` is entered and, in multi-agent mode, which beam recordings x made. Candidates are built one choice at a time in a backtracking tree. Each candidate is checked by simulating the *set* of places the agent can be in. A dead prefix prunes its subtree. Nothing is memoised across branches: there is no table indexed by (window, story index, place). |
| free moves | **Enumerate simple walks.** Every simple walk of silent moves inside a window is listed, by DFS with a visited set *per walk*. This is not a closure or BFS. It is cached only per (start place, window kind), which is a pure function of the map. A step cap raises `OracleError` instead of hanging. |
| `consistent_intervals` (Problem 2) | **Build the timeline explicitly.** For ICRA case 1..6 the timeline gets the four boundaries `t0, tf, t0', tf'` in the case's order, and windows flagged "story on" or "sensors on". Every placement of the story boundaries among the recordings is enumerated, and each timeline goes through the same interleaving search. The model is `docs/notes/paper-examples-icra.md` §1: the agent is free outside both intervals, in `p_1` at `t0` and in `p_n` at `tf`, and never inside an occupancy region at `t0'` or `tf'`. |
| `shortest_superstories` (Problem 3) | **Generate and test.** All super-sequences of `p` are generated by increasing length (insert 0, 1, 2, … letters, up to `max_extra`), and each is tested with `consistent`. Without `anchored=True`, `p'` may start before `p_1` and end after `p_n`, which is the fixture key `problem3_*`. |
| `closest_stories` (Problem 4) | **Generate and test.** All non-empty strings are generated by increasing number of single edits from `p` (BFS layers over strings, up to `max_edits`), and each is tested with `consistent`. The distance of every optimum is recomputed with `levenshtein`. |
| `shortest_accepted` | Every string of length 1, 2, … is tested (the ICRA `n'`). |
| `superstory_exists`, `any_story_exists` | **Exact existence for unbounded answers.** A consistent `p' ⊇ p` is a walk whose visits contain `p`. Reading the extra visits as unreported ones gives: `p'` exists iff `X+p+Y` is consistent with unreported visits for some rooms `X, Y`, each possibly absent (anchored: both absent). So when the bounded search finds nothing, the answer is `"none"` (proved) or `"beyond"` (exists, longer than the bound). |

Problem 3/4 answers are `Bounded(status, value, stories, bound)`. A test may only conclude
"engine value > bound" from `"beyond"`.

## Witness checkers

| Checker | Input | What it checks |
|---|---|---|
| `check_path_string` | `Result.path_string()` (DESIGN.md "Path notation") | Rooms outside brackets must spell the story. Single agent: one `[v]` per recording, deactivations excepted (`v` is the beam side before crossing, or the occupancy sensor). Multi: `[v]` only for x's own crossings, and every occupancy traversal written `{o}`. `(R)` is an unreported entry. A search over (token, recording, place) finds a timing that realises the tokens. The checker is strict: silent entries must be written as `(R)` and occupancy passes as `{o}`, so a path that leaves them out fails. |
| `check_steps` | `Result.path` (the `Step` list of DESIGN.md: `kind, position, time, story_index, sensor, event`) | Replays the steps one by one: adjacency, window and recording timing (`time == event + 1` for recording steps), story spelling, every recording explained exactly once (single) or at most once with no occupancy violated (multi), and the walk ends inside `p_n`. |
| `check_region_walk` | A walk given as place names (`A, R1, C, R1, o1, ...`), as in the fixtures' `witness_*` keys | Searches the timing of each step. |

`check_steps` depends on the `Step` fields pinned in DESIGN.md. `check_path_string` depends
only on the notation.

## Random instances

The tests draw from three generators:

- `random_region_map`: 2–5 rooms, 0–3 beams with the two sides in two different regions,
  0–3 occupancy sensors, and 1–4 regions of at least two features each. With probability
  1/3 it adds a sensor-only region joining two occupancy sensors, like STAR's R3. The
  regions must be exactly the maximal cliques of the derived `G`, so a reader that gets
  only `G` recovers the same map.
- `random_general_region_map`: the same without the clique condition: single-feature
  (dead-end) regions, both sides of a beam in one region, regions contained in others (as in
  ICRA Fig. 2), duplicate regions, rooms and occupancy sensors touching no region. Used by
  `test_oracle_random.py::test_general_region_maps` (the engine works on regions, so it must
  agree on every valid region map, not only on clique-exact ones).
- `simulate_walk`: a random walk of x, plus, in multi-agent mode, recordings by other
  agents. Its result is consistent by construction.
- `perturb`, `random_story`, `random_history`: near misses and arbitrary inputs.

The tests mix them 40/30/30 (simulated / perturbed / arbitrary).

## Self-checks beyond the fixtures

`test_oracle_self.py` also checks these implications, which hold in the model:

- strict ⇒ unreported visits
- single ⇒ multi
- Problem 1 ⇒ every Problem 2 interval case
- any simulated walk ⇒ consistent, in every mode and interval case

`icra_fig2`'s `G` has one maximal clique that is not a region: the triangle `{A, B, o1}`
replaces `R1 = {A, B}`. `test_clique_regions_give_the_same_verdicts` shows that this does
not change any verdict on the fixture cases.

## Scale

Set `CD_TEST_SCALE` (default 1) to multiply the number of random instances. The default run
takes about a second. `CD_TEST_SCALE=60` takes about 40 s, with roughly 10k Problem 1
instances. Problems 3/4 search up to `max_extra = 2` (3 when the scale is at least 3) and
`max_edits = 2`.
